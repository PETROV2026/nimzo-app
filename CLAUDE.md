## Project status

Nimzo is a platform for fire-protection companies to digitize inspection, testing and maintenance (ITM) service forms. The repository is at the bootstrap stage: only `README.md`, `docs/` and `.claude/skills/` exist. The monorepo described below is the **target layout** from the README — create it as specified rather than inventing a different structure. Update this file once real `package.json` scripts, test runners and configs exist.

## Commands (planned, run from repo root)

```bash
pnpm install
supabase start              # local Supabase (requires Docker)
supabase db reset           # apply migrations + seed data
pnpm dev                    # all apps via Turborepo
pnpm dev --filter mobile    # mobile app only
pnpm dev --filter admin     # admin panel only
pnpm build | pnpm lint | pnpm format | pnpm typecheck
```

Env files are copied from `.env.example` in `apps/mobile`, `apps/admin` and `services/pdf`, filled with the values printed by `supabase start`. Development always targets **local** Supabase; the cloud project is production only.

## Architecture

Three apps share one Supabase backend (PostgreSQL, Auth, Storage, RLS) and one shared package:

| Path | What | Stack |
|---|---|---|
| `apps/mobile` | Field app for technicians and supervisors (Android tablet, landscape + portrait) | Expo, Expo Router, expo-sqlite + Drizzle, React Hook Form + Zod, NativeWind |
| `apps/admin` | Web panel for administrators (users, clients, branches, systems, service packages, report history) | React, Vite, Refine, Tailwind, shadcn/ui |
| `services/pdf` | Server-side PDF generation, triggered when a report is submitted | Node, Hono, @react-pdf/renderer |
| `packages/shared` | Types, Zod schemas and **form definitions** consumed by all three | TypeScript |
| `supabase/` | Versioned migrations, RLS policies, seed data | Supabase CLI |

Key design principles that cut across packages:

1. **Forms are data.** Each service form (code `F-SER-XXX`) is a JSON definition validated with Zod, stored in `packages/shared/formatos/` and registered there. A single form engine renders it in the mobile app and the PDF service uses the same definition. Adding or changing a form must not require new screens. Supported field types: `N/A / X / OK` checklists, `SI / NO` questions, text, date/time, dropdowns and repeatable groups.
2. **Offline first.** The mobile app works against local SQLite. Sync is just two flows: download catalogs (forms, clients, branches, packages) and upload submitted reports with photos and signatures. Don't add other sync paths.
3. **Service packages** (per branch and frequency: weekly, monthly, quarterly, annual) generate all the forms for a visit in one step.

### Report lifecycle

`Activo` (draft, on device) → `Pendiente` (finished, on device) → optionally `Autorización` (cloud, waiting for supervisor approval, only for forms that require it) → `Enviado` (cloud; the PDF is generated and stored in Supabase). Keep these state names consistent across the mobile DB, Postgres and the admin panel.

Roles: **técnico** (fills, signs and submits), **supervisor** (signs and authorizes), **administrador** (web panel only).

## Rules

- **Security:** public sign-up is disabled, because only admins create accounts. RLS is enabled on every table. Photos and signatures live in private Storage buckets and are served through short-lived signed URLs. `SUPABASE_SERVICE_ROLE_KEY` is used only in `services/pdf`, never in `apps/mobile` or `apps/admin`.
- **Database changes** go only through versioned migrations in `supabase/` (`supabase db push` in production). No manual changes in the Supabase dashboard. Use the `supabase` and `supabase-postgres-best-practices` skills for schema, RLS and SQL work. `docs/ai/supabase/` is reserved for SQL style, migration, function and RLS guides (currently empty).
- **UI:** `docs/ux-principles.es.md` (Spanish) is the UX rulebook for any interface work: Hick/Fitts/Miller, form design, WCAG 2.1, loading states. Apply it when designing screens.
- **Language:** code, comments, identifiers and file names are in English. The README and user-facing docs are in Spanish.
- **Git:** `main` is protected and only receives PRs. Branches are `develop`, `feature/<name>` and `fix/<name>`. Commits follow Conventional Commits (`feat:`, `fix:`, `docs:`, `refactor:`, `chore:`). Don't add AI co-author or "generated with" attribution to commits or PRs.
- **Deployment:** mobile via `eas build --platform android` + `eas submit` (Google Play internal testing), with `eas update` for OTA. Admin is a static Vite build. The PDF service deploys from `main` to Railway or Render. Native `android/` and `ios/` folders are generated by `expo prebuild` and gitignored.
- Project-local Expo, EAS, shadcn, Supabase and React Native skills are installed in `.claude/skills/`. Use them for work in their areas.
